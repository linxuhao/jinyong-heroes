# Development note — 2026-09-15

武虾传奇 · Myth of Kungfu Shrimp

The last public update here was dated 2026-09-05, and the demo build on the
`demo` branch was made on 2026-09-04 from source commit `6f3bc60`. Development
did not stop; the publishing did. This note closes that gap. Everything below
names the commit that carries it, so anyone reading can check the claim against
the history rather than take our word for it. The private source range is
`6f3bc60..5b598e9` — 779 commits.

Two honest framings before the list. First, this is text only: the playable
demo is **not** republished today, because the demo's content boundary is being
reworked and shipping a build ahead of that rework would publish the wrong
thing. Second, most of the work in this range is unglamorous — it is the kind
of repair that stops a game losing your progress. That is the part of a
development log that usually gets skipped, so it goes first.

## Your progress stops disappearing

- **A refused save no longer destroys the save you already had** (`f4bbda3`).
  The save writer deleted its recovery copy one line *above* the step that
  publishes the new file. A publish that was refused then found no backup, took
  the "there was no previous file" branch, and deleted the file it had just
  promoted — the save that existed before you pressed the button was gone, with
  nothing left to restore from. A second bug in the restore path removed the
  real file and then deleted the backup whether or not the restoring copy had
  worked, so a failure left *neither* copy. Both paths are repaired; the backup
  is now kept when a restore copy fails. Stated plainly: no envelope this build
  writes can actually be refused at that step, so this was defensive safety
  rather than a repair of an observed loss — but it was one code path away from
  being real.

- **A reloaded month cannot hand out its 机缘 a second time** (`f3e7c56`).
  Reloading a month re-granted the reward that month had already given. Save,
  reload, collect again was a working exploit. It is not any more.

- **A new campaign inherits nothing from the last one** (`ad6dda4`). Starting a
  new game reset your profile, dice and decks but left the growth ledger and
  its damage marker behind, so allocation could arrive already refused in a
  brand-new game and an ordinary save could write the previous campaign's
  damaged marker into it. The same change stopped the growth panel from
  overwriting a real failure message with the generic "pick a target"
  instruction — a failed write used to reach you as advice.

- **Every campaign now carries its own identity from the moment of creation**
  (`a4c3130`), minted from the engine's cryptographic RNG and independent of
  the game's seeded dice — so two campaigns rolled from the same seed stay
  bit-identical in their randomness while remaining two distinguishable saves.

## The month is the plan

- **The monthly plan became the month itself** (`f714f5f`, with the segment
  work in `033c191`). The plan used to be one row on a list of ten, so a month
  opened on the action list and you had to go *find* the plan. Now every route
  that reaches a spendable month — accepting the card, reloading, the
  controller's own staging — lands on the plan, seeded with one real row per
  declared slot, so an untouched month is already confirmable and the action
  list is one Back away. A confirmed month refuses its rows by name instead of
  quietly spending itself twice.

- **A commission is raised before it is sealed** (`189c217`), so you see what
  a plan row is going to cost and do before it becomes a fact.

- **The yearly event reroll is reachable again** (`c53183a`). Making the plan
  the month removed the screen the reroll button used to live on, which left
  the reroll unreachable — a feature stranded by its own route being deleted.
  It is now a row on the travel offer, spending the same single reroll budget,
  with the replacement offer, the randomness it consumed and the used counter
  landing in one write.

## What reaches the screen

- **The game stopped speaking to you in its own internal vocabulary**
  (`98eb07d`). The plan editor printed raw internal ids in its target rows
  (`shaolin_yijin_d`) and the contract's own error codes in its status line
  (`slot_count_mismatch`). The reason it survived is worth saying: nothing in
  the project looked at what a player-visible string *looks like*. The two
  known cases turned out to be the visible part of 15 display sites carrying an
  internal identifier onto a screen. The codes still exist where code should
  read them; what changed is what reaches a label, and the shared wording table
  went from 75 refusal codes to 119 so there is a sentence for each. A check
  now fails the build when a module whose verdicts reach a screen emits a code
  nobody has written a sentence for.

- **The fighters fit on their tiles, and their nameplates stop covering them**
  (`ffa8760`). The player character was the one body in the prologue without
  the one-tile clamp its opponents had, so it drew two tiles tall and reached
  into the row above, under the neighbours' name plates. Separately, the
  nameplate packer resolved plate-against-plate but not plate-against-*body*,
  which is how one unit's plate ended up parked on the player's head and the
  player's own plate on its chest. Earlier in the range, neighbouring units
  stopped sharing a single nameplate and HP readout (`724c000`).

- **One damage rule, in one place** (`bde1ecc`), and **a basic attack now
  honours the reach the character declares** (`d28843c`).

## Co-op, and what the demo is

Co-operative play is a development goal and is still not a released feature —
but it stopped being a sketch in this range.

- **A table of one to four players, with an identity and a way out**
  (`b75f31e`), reached from a title-screen entry (`703041f`).
- **A host can name a table, save it, and continue it later** (`96854c8`): the
  ledger, the seats and each player's read position survive reopening
  (`0c87131`).
- **A co-op table can reach a live encounter built from the profile you
  actually played** (`27a470a`), with the turn boundary recorded as a
  durable command (`7465073`) and the round reset reaching the record rather
  than only memory (`35a472e`).
- **One game, one code path** (`21f49d1`). This is a user direction rather than
  a technical one, and it deleted work: the demo used to get its own prologue
  ending, which meant maintaining a second experience alongside the first. That
  ending is gone. The demo is now the same game, and the only difference a
  player meets is that the co-op entry is visible and refuses to open.

## How we check our own work

Two changes in this range are about the tests rather than the game, and they
belong in a public log because they are the reason the rest of it is
trustworthy.

- **A check that ran on four files out of 164 was reporting on four files**
  (`af695f4`). A previous commit had fixed the checker's sensitivity and left
  its window at a four-scenario sample; a green result from that sample is a
  verdict about the sample. It now runs over every scenario, with the scenario
  count itself asserted so a broken file glob cannot make it pass by finding
  nothing.
- **The author of a scenario no longer picks the node that judges it**
  (`351c43a`).

## What is next

A reliable playable slice where different training decisions visibly change

build can come back. The demo republish is deliberately held behind that
boundary work; when it moves, it will be said here.

## Added later the same day — the tool that publishes this page

Three more changes were merged after the note above was published, and none of
them touch the game. They are about the machinery that puts this page in front
of you. They are here because the failure they fix would have been plainly
visible to you and completely invisible to us.

- **This page was one command away from being silently replaced by a ten-day-old
  copy of itself, reporting success** (`5db68d8d`, `946823e5`). The publisher
  took its source checkout from a hardcoded default path, and that path pointed
  at a second, stale clone of this same repository — left at 2026-09-05 while
  development moved on. Every check the publisher had still passed on that
  clone, because its own file list agreed with its own files: the checks
  verified that the manifest and the files matched *each other*, never which
  tree this was. A bare invocation would have restored the superseded front
  page, dropped this note from the site entirely, and exited 0. The tool now
  refuses a bare invocation instead of guessing, and whoever publishes has to
  name the checkout they actually prepared.

- **What was published before is archived rather than overwritten**
  (`5db68d8d`). A front page this publisher did not write is now kept verbatim
  under `notes/archive/`, each body listed with its sha256, so a republish adds
  a generation instead of erasing one. The 2026-09-05 front matter is there.

- **Two checkouts of one repository cannot be told apart by asking which
  repository they are** (`d5fced01`). The obvious defence for the bug above is
  to make the publisher check that the tree it is publishing belongs to this
  project. That defence does not exist: both checkouts carry the same `origin`
  URL, and the stale one's commit is in this repository's own history — it is
  not another project, it is an old copy of this one. Measured from inside the
  stale tree, even "is this commit a descendant of `origin/master`?" answers
  yes, because that tree supplies its own `origin/master`. So the payload now
  declares which *generation* of the publication it is, and the publisher
  refuses a payload older than the generation it knows about. It reads that
  from the manifest bytes alone, so the check still works with no network and
  no repository access at all.

Nothing in this section changes the game. The reason it is published is that a
development log whose publishing tool can quietly revert the log is not a
record of anything, and we would rather say that here than fix it quietly.

## Later the same day — two tests that measured the machine, not the game

The first section was about the tool that publishes this page. This one is
about the play-test harness, and it ends with a failure rather than a merge.

Two of our scenario tests pinned a claim about the game to a **frame number**.
One said "by frame 210 the interface must no longer be showing the waiting
state"; the other said "on frame 270 it must be the enemy's turn". Both were
green for weeks. Both were measuring the computer they ran on.

An enemy turn does not last a fixed number of frames. It ends when a set of
animations finish, and those are bounded by **wall-clock** timers — in
`scripts/autoload/combat_manager.gd`, `_await_tween_safe` waits on a
`SceneTreeTimer` and burns one frame per iteration. The number of frames an
enemy turn spans is therefore its time budget divided by *the cost of one
frame*. Make frames more expensive and the turn ends earlier in frames while
taking the same amount of time.

Measured — same tree, same test, same input, once idle and once with 32 busy
processes on 16 cores:

| scenario | enemy turn, idle | enemy turn, loaded |
|---|---|---|
| `skill_bar_waiting_state` | frames 131–281 | frames 131–204 |
| `camera_transform_follows_unit` | frames 161–340 | frames 161–238 |

The start is identical in both conditions — it is anchored to a player input.
The **end** moves by 77 and 102 frames, while the wall clock moves by 4 ms and
58 ms. Frame 270 is inside the enemy turn on a quiet machine and outside it on
a busy one.

The fix was not to move the frame number to one that passes today. Both
scenarios were **re-derived**: the claims now read counters the engine itself
keeps, which accumulate over *every* frame the enemy turn owns, so they cover
the whole turn instead of one sample of it, and they do not move when a frame
gets more expensive. Coverage went up: 8 asserts became 11 in one scenario,
13 became 20 in the other. Nothing was renumbered, relaxed, deleted or skipped.

Chasing the first one also turned up a **real defect** hiding behind it: the
waiting-state overlay genuinely leaked one frame into the player's turn. One
frame wide, which is why sampling had missed it. `scripts/ui/hud.gd` now
refreshes on the phase-change signal instead of relying on a per-frame poll,
and the engine counts the leak so the test can assert it is zero rather than
hope a probe lands on it.

Both repairs are proved the same way: before the change the untouched test is
**green idle and red under load**; after it the re-derived test is **green in
both conditions**, with the wall clock nearly doubling in between to show the
load was real.

Commits `85c64cdd` and `7c6a7a4f`.

### Why this is not merged

Neither commit is on `master`. We ran one gate covering both, and it failed —
on a **third** scenario, `basic_attack_free_at_zero_qi`, which pins "the attack
has resolved" to frame 120 while the attack is confirmed at frame 80. Run on
its own that scenario resolves at frame 85 on both the patched tree and the
unpatched one — identical, so the two fixes above did not cause it. In the
full 164-scenario batch it had not resolved by frame 120.

So the same disease has three instances, we have fixed two, and the third is
what is holding the merge. That is the honest state of it. We are not merging
past a red gate, and we are not narrowing the gate to make it green.

What this cost us, stated plainly: the second instance sat in the tree the
whole time and we only looked at it because the round that fixed the first one
pointed at it on its way out. The third we did not find by reading the code at
all — the gate found it. Several claims in our own work orders turned out to be
wrong when the rounds checked them, including one measurement we had attributed
to the wrong scenario.

### Update, an hour later: the gate is green and it is merged

The section above was published while the gate was red, and said so. Here is
the close.

The third scenario turned out not to be the same defect after all, and the
round that took it said so plainly instead of making the story fit. Nothing
was drifting past frame 120. The scenario walks the player three tiles with
three key presses ten frames apart, one step of the walk animation takes nine
to eleven frames, and **input arriving during a step is silently discarded**.
When frames cost slightly more, the second press lands inside the first step
and is gone; the player stops one tile short, the target is out of melee
reach, and the attack never happens at all. `acted` is not late — it never
becomes true.

Two things we had assumed were wrong and got measured out of the way: it is
not inherited state between tests (each test gets a throwaway home, and in the
same run an untouched copy was green beside an instrumented copy that was
red), and it is **not CPU load** — 48 runs under heavy load produced zero
failures, the opposite of the first two scenarios. The axis is per-frame work
inside the process, and it is a per-run coin flip: sixteen copies of the same
test in one request gave four failures on the old code and zero on the new.

All three claims now read counters the engine keeps over the whole interval.
One gate covered all three and passed every stage: 357 of 357 scripts compiled,
**164 scenarios and 4105 assertions**, 54 GDScript suites. Merged as `462abd4`.

Two things we found and did **not** quietly fix, because they are separate work
and hiding them in this one would have made the diff lie:

- Four more scenarios march at the same ten-frame gap against the same
  nine-to-eleven-frame step. They pass today the way this one passed for
  weeks. The card for them requires scanning *every* scenario to prove the
  list is complete, because sampling is precisely how this survived two gates.
- The silent input drop is a **player-facing bug**, not just a test one. The
  mouse path already queues the steps you clicked; the keyboard path throws
  them away for 0.15 s per tile. So in this build a mouse can walk three tiles
  and a keyboard sometimes walks two, with nothing on screen to say why. That
  is now its own card.

We also found that our own test harness could not have shown us the dropped
press: the field that reads `pressed: true` is computed from the test script,
not from the run.
