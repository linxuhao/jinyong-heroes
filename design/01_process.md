# 01 · 开发循环与排序规则

> `00_roadmap.md` 定的是**阶段顺序**(做哪一层),本档定的是**循环**(一轮怎么跑)
> 和**排序规则**(两件事同等紧急时先做哪个)。
> 立此档的直接原因:2026-09-01 owner 问「开发 cycle 我们好像没有设定规定,一般是怎么做的?
> 先做零件再拼装、先整体 playability 再细节 —— 这样吗」。当时确实没有成文的规矩,
> 排序全靠每轮试玩的实测证据临时定。证据驱动是对的,但**没有成文的平局裁决规则**,
> 于是踩了下面「§3 我们踩过的坑」里的那一脚。

---

## 1. 不是「由零到整」,是垂直切片加厚

本项目**已经**有一条从头到尾能玩的最细路径(创建 → 修炼 → 遭遇 → 江湖 → 结局),
`00_roadmap.md` 的第 1 阶段就是这件事,已完成。所以我们不在「先做零件再拼装」的阶段,
而在**加厚一条已经贯通的脊柱**。

推论,对每一轮 brief 都成立:

- **一轮只加厚一层,不新开一条脊柱。** 新系统若不能挂在已有的六段上,不进这一轮。
- **加厚必须端到端。** 「数值算对了」不算加厚,「玩家在屏幕上看得到这次选择的后果」
  才算(见 §3 的 facility 案例)。

## 2. 排序规则:按「这一层还成不成立」逐层往下压

`00_roadmap.md` 的五阶段表(逻辑 → 交互 → 内容 → 美术 → 数值)大体正确,
但它隐含一个前提:**上层是对的**。而本仓的实测反复证明相反 ——
上层看起来没问题,其实是坏的。所以平局裁决用下面这张表,自上而下:

| 层 | 这一层问的问题 | 判它成立的证据形态 |
|---|---|---|
| L1 能不能玩 | 走完全程会不会卡死 / 打不了 / 进不去 | 一条**只用真实输入**的全程场景绿 |
| L2 规则成不成立 | 有没有被短路的兑换、无限刷、白拿、零消费的属性 | 边界值实测,不是断言变量被赋对 |
| L3 选择算不算数 | 三年的经营改不改变结局 | 多路线跑到结局的**差分**表 |
| L4 看不看得懂 | 玩家读得到刚才发生了什么吗 | 动作前后两帧,玩家可读的东西不同 |
| L5 好不好看 | 美术、动画、音效 | 人工看帧 |

**L2 在 `00_roadmap.md` 的表里没有独立的位置** —— 它被摊在「逻辑」和「数值」两头,
两头都不认领。这正是它长期失守的原因,补在这里。

**顺序是硬的:低层没成立之前,不投高层的轮次。** 理由不是洁癖,是成本:
L4 的一轮是在给一个 L2 已经坏掉的游戏化妆,那一轮的产出会在 L2 修好之后重做。

## 3. 我们踩过的坑(为什么 L4 不能提到 L2 前面)

`theme` 轮(L4,2026-08-31)开跑的时候,游戏里同时躺着:

- **修炼主循环的永久软锁** —— `scripts/segments/cultivation.gd:265-267`,
  无可选功法时 `phase = "ACTION_PICK"` 却不调 `_after_action()`,月份不推进,回车按到死。
  当时 **78 条场景全绿**,因为它们都走 `debug_fast_forward` 绕过了这条路
  (`:684-686` 的同一分支是对的)。这是 L1 缺口,被 L1 的闸门放过了。
- **少林设施是台无限兑换机** —— 10 秒可把结局从最低档刷到最高档。L2 缺口。

`theme` 轮自己又**引入了三处遮挡**(门派选择 ×5 场景、教程浮层、名册面板),
两道闸门都没拦住:可读性闸门的 Q6 问的是「有没有截断的文字」,**截断不是遮挡**。
这三处是我自己逐帧比对发现的,不是闸门发现的。

代价是清楚的:如果先 L2 再 L4,`theme` 就是在给一个已经成立的游戏抛光。
实际发生的是,L2 的 `loop` 轮修完软锁和兑换机之后,`theme` 的一部分产出要重做。

**同一层里也有这个坑。** `loop` 轮(L2)的修法是给设施加「每人每月上限」,
而 `cultivation.month` 在江湖阶段冻结在 12 —— 全程只允许 2 次设施使用 = 16 两,
而产出是 1830~2215 两。修一个无限兑换,修出一个 2148 两花不掉的死钱。
**一个上层的绿灯是拿下层的什么换来的,必须在 brief 里问出来。**

## 4. 一轮的形状(循环)

```
① 试玩取证   —— 派 subagent 真玩,拿实测帧 / 代码行号 / 数字回来
② 写 brief   —— 每条卡必须带「修好之前红的那一次的实测值」
③ 发轮       —— 只经 butler 发起,run 存在后立刻挂断(两个驱动者是多一个)
④ 边跑边玩   —— 同时派试玩 subagent 玩上一轮的产物,产出下一轮的证据
⑤ 逐闸判裁   —— 每个 checkpoint 对着我自己核过的证据判,不看它的自述
⑥ 验交付     —— design/ 无 validation,我自己验;含 99_changelog.md 的只增不删检查
⑦ 更 roadmap —— 用 ④ 看到的,不是用 brief 承诺的
```

④ 与 ①/⑦ 是同一件事的两头:**下一轮的排序由这一轮跑的时候玩到的东西决定**,
不由本档的表决定。本档的表只在两件事同等紧急时当平局裁决。

## 5. 三条不可让步的规矩

1. **先有实测的红,才准有绿。** 一条卡若说不出「没修之前这个钉子红在哪个实测值上」,
   它证明不了任何事。`facility_use_reusable` 47 条断言全绿,而使用前后的 8 帧 PNG
   逐字节相同(md5 `e5010a5095349f67913d15f888e1a18f`)—— 断言证明的是变量被赋对了,
   不是玩家看得见。
2. **钉性质,不钉字面量。** 「存在一个 Label」「text == '银两 −8'」「at: 570」这类
   形态断言,合法改动会误红,而它们挡不住「有 Label 但内容不变」。
   钉 `changed`,钉差分,钉不变量。
   反例:`tests/test_playtest_contract_smoke.py` 里有过双反斜杠的正则
   (`rf"^name:\\s*{name}\\s*$"`),**永远匹配不上**,守卫存在但从不生效。
3. **绿灯盖在「没有」上面,等于没有闸门。** 本仓这一族缺陷已单独成档(见 memory
   `aitelier-pass-on-absence`)。最贵的一次:`ui_occlusion_watch.gd:58` 每帧崩溃
   44,660 次,崩在 `violations` 赋值之前 —— 之前那些绿灯是**没扫过任何一帧**的假绿。
   闸门必须**构造上不可能崩**,并且崩了要显性红,不能静默放行。
